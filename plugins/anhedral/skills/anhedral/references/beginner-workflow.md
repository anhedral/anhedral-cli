# From app idea to working app

The primary entry is a conversation: “Build a shared reading list for my team.” Infer a small first version with observable criteria: save a link, list saved links, mark one read and search it. Clarify ownership/authentication only if the intended users or privacy boundary are unclear. Explain the stack in one sentence: a web app on Cloudflare Workers with Neon for shared durable data. Add authentication when the agreed privacy requirements require it.

1. Inspect the host's callable tools and coding environment. Record tool availability, local checkout/runtime, provider account/scope and successful integration checks separately. A connected Neon plugin may work while a local Neon CLI remains unauthenticated. Use the connected integration where it covers the operation; record the CLI limitation without blocking unrelated coding.
2. Show the selected stack before code exists using a minimal draft in the panel. Capture the brief and target folder; avoid sending the beginner through infrastructure settings. For this example inspect `pnpm dlx anhedral@<registry-version> new <directory> --next --neon --dry-run --json`. Check required permissions/resources and then generate into the intended empty folder. Use the local built CLI for unpublished changes.
3. Register the generated folder with the draft ID and read its requirements. The generated web application uses OpenNext and the database starter uses Drizzle and Hyperdrive. These are source/configuration starters. Discover existing resources in the intended account/environment before creating a Neon project/branch and Hyperdrive configuration. Provision through available provider tools, APIs/CLIs or browser control; do not add a separate provisioning engine.
4. Wire the actual resource IDs and bindings. Keep database credentials in ignored environment files/provider secrets, use appropriate migration/runtime roles, and verify Hyperdrive database connectivity with query caching disabled for correctness-sensitive reads. Review/apply the product schema and implement the reading-list flows, authorization and useful failures. Generated schemas and provider configuration do not count as product acceptance.
5. Run project checks, an OpenNext Worker build and a working preview. Exercise saving a link, reading it back after restart, marking it read and searching. Test the agreed authorization boundary. Report an observed database connectivity failure independently even if the Worker deployment succeeded. Keep the preview link and the exact next needed action visible.
6. Prepare the concrete production version, migration impact, operating owner and rollback procedure. Use existing release authorization or request only what is missing. After deployment, exercise the same flows at the live URL in the intended environment. Report the live link with evidence and remaining limitations; an accepted deployment request is not release verification.

Update the canonical non-secret `anhedral.progress.json` work record as each observation changes. Use `readProjectProgress` / `updateProjectProgress` from the npm API or `anhedral progress <directory> --json` to read and `anhedral progress <directory> --update <report.json> --json` to report. Updates require the last observed `expectedRevision`; reload after a conflict instead of overwriting another reporter’s observations. Include the capability and environment, dated evidence with source/configuration/revision/account/resource identity as applicable, blocker and next action. Agent-reported milestones are evidence supplied by the executor, not automatic independent verification. In the panel use `anhedral_report_observations` with `projectId` and the snapshot’s `work.revision` as `expectedRevision` (0 when absent). Its result returns the updated stack snapshot; report selected scope first when no record exists. Keep generated requirements unchanged.

On restart, read the work record and inspect current source/configuration and provider identity. Reuse the existing database/Worker when they still match; stale evidence does not justify duplicate resource creation or skipping failed checks. A missing tool is a specific access gap, not a reason to claim the whole stack is ready. Do useful independent work while access is unavailable.

The same conversational flow applies to Expo mobile, Electron desktop, WXT extensions and Hono APIs. The initializer constructs their supported starters; Codex completes the selected platform SDKs, device/packaging checks and integrations using existing tools. Domain registration, Cloudflare mail, Containers and architecture alternatives are direct integrations rather than supported generator flags. Existing applications need targeted reviewed changes because applying complete starter overlays could replace edited code.

The bundled panel runs locally through Node stdio MCP. A cloud ChatGPT host cannot inspect local folders merely because the plugin is installed. Public ChatGPT distribution needs hosted HTTPS MCP, cloud-safe storage/authentication and directory submission. These are deployment/distribution requirements, not completed capabilities of the local plugin.
