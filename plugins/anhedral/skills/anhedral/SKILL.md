# Anhedral

Start from a plain-English app request. The user should describe what people need to do, not choose infrastructure or complete a setup dashboard. Codex executes the work using the host's available tools; this plugin guides decisions, the `anhedral` npm package constructs the foundation, and the panel shows the app, selected stack, current progress, next needed action and preview/live link. Continue from actual project state instead of restarting.

Read [the stack standard](references/application-stack-standard.md) when selecting architecture and [the beginner workflow](references/beginner-workflow.md) for the end-to-end flow. Inspect source, manifests, instructions, Git state and provider configuration before changes. Preserve existing work and accepted architecture; never run `init` over an existing application. The initializer has no safe incremental `add` command: extend existing code deliberately and review conflicts.

Establish intended users, interfaces, core workflows, data and observable acceptance criteria. Infer established choices and ask only for consequential missing information. Select only necessary apps/services and explain the choice briefly in product terms. Default web hosting to Cloudflare Workers + OpenNext; use shared Hono APIs when additional consumers justify them.

Observe execution access before promising work: callable session tools, shell/Node/pnpm and checkout, authenticated provider account and scope, and successful integrations are separate facts. An installed plugin is not a callable tool; credentials or plugin OAuth are not CLI/CI authentication. Use connected provider tools first, scoped APIs/CLIs next, and browser/computer control for dashboard-only work. Discover real alternatives when a capability is unavailable; never invent a tool, successful grant or deployment.

When panel tools are available, open the stack with `anhedral_open`, save a minimal draft using `anhedral_create_project`, and register generated code with its `draftId`. Use `anhedral_plan_stack` for selected scope. Keep infrastructure and diagnostic details behind the app overview. The panel is a visual companion; it does not execute provider provisioning. Only register the intended folder/account/environment. Tool results refresh the open panel; a standalone preview copies agent requests for use in an executing host.

Use [setup](references/setup.md) for account access, generation and infrastructure. The versioned [capability registry](references/capabilities.json) defines generated starters and remaining integration work. Run a pinned CLI dry-run before generating into an empty destination. Keep `anhedral.setup.json` as its immutable generated requirements plan: it never becomes completion evidence. The CLI supports application starters across web, mobile, desktop, browser extensions and APIs; domain/mail, Containers and other deliberate architecture adaptations require direct integration using the host's tools.

Persist observed milestones separately in the versioned `anhedral.progress.json` project work record. Use `anhedral_report_observations` when available, with `projectId` and the snapshot’s `work.revision` as `expectedRevision` (0 when absent). Report the selected plan first when no record exists. Each tool result returns the updated stack snapshot to the panel. The npm API exposes `readProjectProgress` / `updateProjectProgress`; the CLI exposes `anhedral progress <directory> --json` and `--update <report.json>`. Reload after revision conflicts. Keep environment/account/resource/revision identity, dated non-secret evidence, blockers, next action and preview/live links. Report each selected capability independently: provisioning, connectivity, product checks and deployment can differ. A deployment accepted by a provider does not prove the app works. Distinguish agent reports from independently checked provider facts. Recheck stale source/configuration/account/resource observations on resume and reuse existing resources. Do not duplicate this record in a second handoff database. Existing ordered checklist tools are detail views, not a requirement for the beginner to administer infrastructure.

Implement actual product behavior, authorization and integrations before completing a starter. Use specialized provider/framework/design skills for their actual scope. Exercise acceptance criteria and browser/native flows, then use [delivery](references/delivery.md) for release checks and post-release verification. Update progress as work proceeds, including failures and interruptions. When external access is blocked, record the exact next needed action and continue independent implementation. Do not report unperformed external checks as successful.

The bundled Node stdio MCP server is a local Codex/desktop integration. A public cloud ChatGPT app requires a separately hosted HTTPS MCP service, cloud-safe storage/authentication and directory submission; a local plugin installation does not make local folders or shell tools available in cloud ChatGPT. When the host lacks required execution access, explain the specific limitation and provide concrete next steps.

Respect existing authorization. Setup is not blanket permission to accept terms, activate paid plans, broaden access, send messages or release production. Prepare concrete reviewable changes before requesting missing authorization; do not ask again for approved actions within scope.
