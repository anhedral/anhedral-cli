# Stack standard

This is the architecture standard for applications generated by Anhedral. Use it to select components and decide where code belongs. Follow the [software factory](software-factory.md) to implement and deliver the product.

The default web foundation is Vinext, React, TypeScript, Tailwind, shadcn/ui and Lucide on Cloudflare Workers. Every project uses pnpm workspaces and Turborepo. Add components for a concrete product requirement; the default does not include a database, identity provider or every available service.

## Defaults and foundations

| Area                            | Default behavior                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Application                     | Vinext web app; Cloudflare hosting                                                                   |
| Workspace                       | pnpm workspaces, Turborepo and one root lockfile, including single-app projects                      |
| Shared tooling                  | `packages/typescript-config` and `packages/eslint-config`                                            |
| Web UI                          | Shared `packages/ui`, shadcn/ui conventions, React, Tailwind and Lucide                              |
| Cloudflare delivery             | Void for supported selections; explicit OpenNext, Queues and Basin use Wrangler                      |
| Runtime                         | Node.js `24.21.0+` for Void; pnpm `10.34.5`                                                          |
| Configuration                   | One root `anhedral.json`; application tooling stays beside its app                                   |
| Data, identity and integrations | Opt-in; no database, authentication, billing, email or analytics service is selected by plain `init` |
| Generation                      | Source and dependency setup; no cloud provisioning, deployment or automatic source commit            |

The registry contains 28 selectable products and four foundation entries: `workspace`, `typescript`, `eslint` and `ui`. The first three accompany every project; `ui` accompanies web applications. Product flags select recipes; the resolver supplies required foundation dependencies.

## Select the applications

| Need                           | Selection                     | Destination and generated architecture                                                              |
| ------------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------- |
| Web on Workers                 | Default, or `--vinext`        | `apps/web`; Vinext, Vite and React on Cloudflare                                                    |
| Native Next.js on Vercel       | `--next`                      | `apps/web`; native Next.js and Vercel configuration                                                 |
| Next.js on Workers             | `--next --hosting=cloudflare` | `apps/web`; OpenNext adapter and Wrangler delivery                                                  |
| API shared by multiple clients | `--hono`                      | `apps/api`; Hono Worker with OpenAPI/Zod contracts and health route                                 |
| iOS and Android                | `--expo`                      | `apps/mobile`; Expo, React Native, Expo Router, NativeWind and React Native Reusables configuration |
| Desktop                        | `--electron`                  | `apps/desktop`; Electron, React, Vite, isolated preload and platform packaging configuration        |
| Browser extension              | `--wxt`                       | `apps/extension`; WXT/React Chrome side panel with user-triggered active-page access                |

For example, `--vinext --hono --expo --neon` selects web, an API, mobile and PostgreSQL. Explicit application flags replace the default application selection: `--expo` alone selects mobile, and `--hono` alone selects the API. If only add-ons are requested, the resolver includes a default web app: `--neon` selects Neon and Vinext. Vinext and Next.js are alternatives. Native Next.js defaults to Vercel; Vinext uses Workers.

Use server routes inside the web app when it is the only consumer. Add Hono when mobile, desktop, extensions or independent clients need a shared API. Browser and device clients access server endpoints; they never import database factories or receive server credentials. Check actual Vinext behavior in its Worker runtime rather than assuming native Next.js parity.

## Select data and identity

| Selection       | Destination and generated scope                                                                                          | Required implementation/setup                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `--d1`          | `packages/db`; Drizzle/D1 factory, schema and explicit migration tooling; `DB` Worker binding                            | Create/reconcile the database, define product tables and review SQL; one deployment migration owner |
| `--neon`        | `packages/db`; Drizzle/Neon HTTP factory, schema and transactional migration tooling                                     | Select project/role, configure runtime and separate direct migration connections, review SQL        |
| `--better-auth` | `packages/auth` and database schema; auth routes on the selected server                                                  | Private secret, public auth origin, migrations, sign-up policy and resource authorization           |
| `--clerk`       | Web provider, sign-in/up pages and middleware when web is selected; `packages/auth` backend helper when Hono is selected | Configure keys, origins, protected routes and native client integration as needed                   |
| `--local-data`  | `packages/local-data`; async read/write interface                                                                        | Implement platform-specific SQLite/filesystem adapters, offline behavior and synchronization        |

D1 is the standard choice when Worker-local SQL fits. Choose Neon when the application needs PostgreSQL semantics. Better Auth supplies application-controlled identity; Clerk supplies hosted identity. Hosting audience protection is a separate access layer from either choice.

## Select services

| Selection         | Destination and generated scope                                                                                         | Required implementation/setup                                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `--r2`            | Selected server's private `FILES` binding and `private-files.md`                                                        | Authorized upload/download/delete endpoints and file ownership checks; no public bucket or generic file API is generated                 |
| `--kv`            | Selected server's `CONFIG` binding                                                                                      | Keys, TTLs and propagation handling; never use KV as transactional authority                                                             |
| `--realtime`      | `apps/realtime`; SQLite-backed Durable Object rooms and WebSocket message forwarding                                    | Authenticate connections, authorize membership, isolate rooms and handle reconnects; public entry returns 501 until implemented          |
| `--neon-realtime` | `packages/neon-realtime`; separate sealing server/subscription client factories and Drizzle adapter                     | Manually activate the selected branch, configure origins and implement authorized queries, renewal and cleanup                           |
| `--stream`        | `packages/stream`; server-only Cloudflare Stream live input factory for WHIP/WHEP broadcasts                            | Activate Stream manually; implement creator/player UI, input ownership, media negotiation, playback privacy and teardown                 |
| `--queues`        | `apps/jobs`; queue producer/consumer, retry limits and dead-letter configuration; producer binding on a selected server | Transactional idempotency, processing and dead-letter recovery; the starter retries messages instead of acknowledging unimplemented work |
| `--cron`          | `apps/scheduled`; scheduled Worker with an hourly starter trigger                                                       | Product schedule, task implementation, overlap policy, idempotency and failure visibility                                                |
| `--workflows`     | `apps/workflows`; durable workflow and a retryable validation step                                                      | Authorized invocation, product steps, retry/resume/cancel behavior and recovery                                                          |
| `--workers-ai`    | Selected server's `AI` Worker binding                                                                                   | Model calls, authorization, input handling, usage and spending limits                                                                    |

`--realtime` and `--neon-realtime` are independent and can coexist. The former supplies room-based messaging infrastructure; the latter supplies live SQL query integration. Neither generates a complete collaboration or subscription feature.

## Select SDKs and integrations

| Selection      | Destination and generated scope                                                                                  | Required implementation/setup                                                                                        |
| -------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `--openai`     | `packages/ai`; direct server-side OpenAI SDK factory                                                             | Models, routes, failure handling and usage limits                                                                    |
| `--ai-sdk`     | `packages/ai`; AI SDK `generateText`/`streamText` exports and OpenAI provider                                    | Streaming, tools, cancellation and provider configuration; generated credentials default to OpenAI                   |
| `--resend`     | `packages/email`; server SDK factory                                                                             | Verified sending domain, templates, delivery/bounce handling and webhook verification                                |
| `--stripe`     | `packages/billing`; server SDK factory                                                                           | Products/prices, purchase/cancellation flows, signed webhooks, entitlements and idempotency                          |
| `--revenuecat` | `packages/billing/revenuecat.md`; cross-store integration guidance                                               | Install platform SDKs and configure store products, offerings, purchase/restore flows and entitlement reconciliation |
| `--sentry`     | `packages/observability`; integration boundary and redaction fields                                              | Install/init platform SDKs, configure private source-map uploads and verify alerts                                   |
| `--posthog`    | `packages/analytics`; server analytics factory                                                                   | Event schema, consent, privacy filtering and event delivery                                                          |
| `--basin`      | `packages/analytics`, or `packages/basin` alongside PostHog; event helper and private `ANALYTICS` stream binding | Event schema, ingestion verification and application-specific sink/transformation design                             |
| `--styling`    | `packages/styling`; light/dark tokens and Tailwind v3 preset used by Expo/WXT                                    | Platform typography/components and adoption by other interfaces; automatically selected with Expo and WXT            |

OpenAI and AI SDK are alternative recipes for `packages/ai`; Workers AI can accompany either. PostHog and Basin can coexist: the Basin recipe changes its package destination to avoid a collision. Electron starts with its own renderer styling; shared tokens do not imply one component library across every platform.

The provider adapters can configure selected Neon projects/connections, Clerk applications/keys, Resend domains/sending keys, Stripe account/webhook setup, RevenueCat projects/apps/keys, Sentry projects/DSNs, PostHog projects and OpenAI projects/service accounts. This automation is separate from the generated application integration. See [provider configuration](software-factory.md#provider-configuration) for fields, credentials, permissions and remaining owner steps. Neon Realtime activation is manual.

## Composition and compatibility

| Choice                                                                                | Resolver behavior                                                      |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| No application flag                                                                   | Adds Vinext, or Next.js when Vercel hosting is selected                |
| `--next` without a hosting flag                                                       | Selects Vercel                                                         |
| Vinext with Vercel                                                                    | Rejected; Vinext requires Cloudflare                                   |
| Vinext and Next.js; D1 and Neon; Better Auth and Clerk; OpenAI and AI SDK             | Each pair is mutually exclusive                                        |
| Better Auth without a database                                                        | Adds D1; an explicit Neon selection uses PostgreSQL instead            |
| Neon Realtime without a database                                                      | Adds Neon; an explicit D1 selection is rejected                        |
| Better Auth with Neon Realtime                                                        | Resolves to Neon regardless of flag order                              |
| RevenueCat without Stripe                                                             | Rejected; select `--stripe` explicitly                                 |
| Expo or WXT                                                                           | Includes the shared styling package                                    |
| Database/auth or Neon Realtime without a server                                       | Rejected; select a compatible web app or Hono                          |
| Native Next.js/Vercel with Worker-bound capabilities such as D1, R2, KV or Workers AI | Adds Hono for the Cloudflare runtime                                   |
| OpenNext, Queues or Basin                                                             | Uses Wrangler for all Cloudflare targets in the workspace              |
| Later addition that changes the engine or relocates existing runtime source           | Rejected; `add` does not migrate delivery engines or runtime ownership |

When Hono is selected, it owns the shared database/auth runtime and server resource bindings. Other interfaces consume its endpoints. Worker services such as realtime, cron and workflows have their own deployable applications.

```sh
# Web with D1 and Better Auth (D1 is also the conditional auth default).
anhedral init my-app --better-auth

# Web, API and mobile with PostgreSQL.
anhedral init my-app --vinext --hono --expo --neon

# Vercel web with an automatically selected Hono backend for R2.
anhedral init my-app --next --r2

# Independent room messaging and live PostgreSQL queries.
anhedral init my-app --realtime --neon-realtime
```

The bundled registry is authoritative for exact dependencies, destinations and compatibility:

```sh
anhedral registry list --json
anhedral registry view better-auth --json
anhedral init my-app --vinext --hono --d1 --better-auth --r2 --dry-run --json
```

Append `--dry-run --json` to an initialization command to inspect its resolved products, destinations and setup requirements without writes or network requests. There is no `--all` or external registry support. Recipes create integration foundations; provider resources, credentials and finished features have their own setup and acceptance requirements.

## Organize the source

| Location                                               | Owns                                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `apps/web`, `apps/api`, other selected `apps/*`        | Deployable applications and services, runtime entry points and configuration |
| `packages/ui`                                          | Shared web UI components                                                     |
| `packages/db`                                          | Server-only database factory, schemas and migrations                         |
| `packages/auth`, other selected `packages/*`           | Reusable integration code with explicit inputs                               |
| `packages/typescript-config`, `packages/eslint-config` | Shared tooling conventions                                                   |
| `anhedral.json`                                        | Committed Anhedral configuration and provenance                              |
| `docs/stack.md`                                        | Generated selection, destinations and setup requirements                     |
| `.anhedral/`                                           | Ignored local delivery journals and private state                            |

Use one root `pnpm-lock.yaml` and the root task graph. Keep framework-specific lint dependencies in the consuming app; shared lint configuration stays usable by non-web clients. Shared packages receive bindings, connections and configuration through factories. Extract code around actual consumers, and keep runtime/network relationships explicit.

See the [full-stack example](https://github.com/anhedral/anhedral-cli/tree/main/examples/full-stack) for a source-only composition. It demonstrates the structure; it is not a running production system.

### One Anhedral configuration

The root `anhedral.json` has an envelope with `schemaVersion: 1` and validated named sections. Each section retains its own domain schema. Only selected hosting sections are present.

| Section      | Purpose                                                               |
| ------------ | --------------------------------------------------------------------- |
| `identity`   | Stable application identity and local catalog registration            |
| `setup`      | Products, hosting, environment requirements and owner setup           |
| `standard`   | Scaffold conventions and version provenance                           |
| `registry`   | Recipe versions, generated-file fingerprints and workspace references |
| `providers`  | Nonsecret integration settings and resource selections                |
| `cloudflare` | Delivery engine, account, audience and targets                        |
| `vercel`     | Repository, team, project and audience                                |

Preserve unrelated sections when editing. Credentials and delivery history stay outside this document. Native tooling files remain with their applications: a single Anhedral document does not replace `package.json`, Vite configuration or per-app deployment configuration.

## Data and migrations

All database-backed selections use the server-only `@workspace/db` package:

| Path                            | Responsibility                                        |
| ------------------------------- | ----------------------------------------------------- |
| `packages/db/src/index.ts`      | Factory receiving a D1 binding or connection string   |
| `packages/db/src/schema.ts`     | Shared Drizzle schema, including selected auth tables |
| `packages/db/src/migrate.ts`    | Explicit migration entry point                        |
| `packages/db/drizzle/`          | SQL, snapshots and migration journal                  |
| `packages/db/drizzle.config.ts` | Configuration with paths relative to itself           |

The factory does not load environment files or migrate on startup. Review generated SQL from `pnpm db:generate` before running `pnpm db:migrate`. Both tasks are uncached and excluded from builds and checks. Exactly one server owns deployment migrations; other consumers share the database without becoming migration writers.

D1 manual migration defaults to local. `pnpm db:migrate -- --remote` explicitly targets the configured database in the migration owner's Worker configuration. Void deployment validates an ignored, byte-identical app-local copy against the authoritative shared SQL; the copy is not another migration source.

Neon runtime queries use server-supplied `DATABASE_URL` through the HTTP adapter. Interactive transactions require a reviewed WebSocket or PostgreSQL adapter. Migrations use a transactional WebSocket connection and direct `DATABASE_URL_UNPOOLED` from the environment or `packages/db/.env.local`/`.env`. Test migrations on the intended development branch before production. Runtime provisioning does not supply migration credentials automatically.

## Live video with Cloudflare Stream

Select `--stream` for one-to-many ultra-low latency live video: browser or supported encoder publishes with WHIP and viewers play with WHEP. [Stream Live WebRTC reached GA on October 15, 2026](https://developers.cloudflare.com/changelog/post/2026-10-15-stream-live-webrtc-ga/). It is the preferred broadcast service when a product needs live video. Add it only when needed; it can coexist with `--realtime` Durable Object messaging and `--neon-realtime` live SQL. Many-to-many calls require a separate Cloudflare Realtime design.

The recipe creates `packages/stream` with a server-only `@workspace/stream/server` export. `createStream({ accountId, apiToken })` exposes live input creation and retrieval. It requires a server, works with Vinext, native Next.js or Hono, and adds no Worker resource binding or SDK dependency. Follow the generated package README. Stream activation, live inputs and runtime credentials are configured explicitly; CLI provisioning and `ship` do not automate this integration.

Keep `STREAM_API_TOKEN` server-only and scope it to Stream Write in the customer account selected by `STREAM_ACCOUNT_ID`. Authorize creators, persist input ownership and enforce quotas before management calls. The returned `webRTC.url` is a publish credential: disclose it only to the authorized broadcaster, never to viewers, logs or static assets. Viewer responses contain only the approved WHEP endpoint or short-lived playback token. Choose `requireSignedURLs` explicitly when creating an input; implement and verify playback token issuance for private broadcasts. Hosting access protection does not protect Stream media endpoints.

Media goes directly between the browser and Stream. The application server owns identity, input ownership and endpoint/token issuance. Implement camera/microphone consent, HTTPS, ICE negotiation, user-facing errors, reconnect and session cleanup. Delete signaling sessions, close peer connections and stop capture tracks when a broadcast ends. No finished player, broadcaster or conferencing feature is generated.

As reviewed October 16, 2026, the [WebRTC documentation](https://developers.cloudflare.com/stream/webrtc-beta/) requires paired WHIP/WHEP and excludes recording, WHIP-to-HLS/DASH playback, RTMP/SRT-to-WHEP bridging, restreaming and live viewer counts. Usage is visible in Stream analytics/billing; broadcast and player-experience metrics remain unsupported. The URL retains `webrtc-beta` although the feature is GA. [Delivery billing](https://developers.cloudflare.com/stream/pricing/) began October 15 at standard Stream rates; budget viewer-minutes and check current account eligibility before activation. Verify creator/viewer access, private media denial, cross-tenant isolation, reconnect and teardown against the actual provider before claiming live acceptance.

```sh
anhedral init my-app --stream
anhedral add stream --dry-run --json
```

## Neon Realtime

`--neon-realtime` selects live PostgreSQL query foundations and adds Neon if no database was chosen. It requires a server and rejects an explicit conflicting database. It can coexist with `--realtime`, which means Durable Object WebSocket rooms.

The recipe creates `@workspace/neon-realtime/server` and `/client` exports in `packages/neon-realtime`. The server receives private `NEON_REALTIME_SECRET` and `DATABASE_URL`; the client receives public `NEON_REALTIME_URL`. Follow the generated package README for framework-specific public environment mapping.

Enable Realtime on the intended Neon branch and configure exact allowed origins, secret and endpoint manually. Authenticate sealing requests, derive user/tenant scope from verified identity, and construct bounded read-only queries on the server. Clients subscribe with short-lived sealed queries; implement authorized renewal, reconnect behavior and isolation tests. No arbitrary SQL endpoint or complete subscription feature is generated.

The pinned integration targets the [Neon Realtime beta](https://neon.com/docs/realtime/overview), whose reviewed authorization model has no RLS support. Scope the queries you seal and review the provider's current limits before production use. Recipe tests do not establish live subscription or cross-tenant acceptance.

## Runtime and delivery configuration

| Profile                                           | Engine and configuration                                                                                                   | Project runtime floor              |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Supported Cloudflare selections                   | Void `0.27.0`; app-local `anhedral.cloudflare.json`, `void.config.ts`, `env.ts`, `env.example`, committed `void.lock.json` | Node.js `24.21.0+`                 |
| Explicit OpenNext, Queues/DLQ or Basin            | Wrangler; app-local `wrangler.jsonc`                                                                                       | Node.js `22.13+` on 22.x, or `24+` |
| Native Next.js/Vercel and other non-Void profiles | Native framework/platform tools                                                                                            | Node.js `22.13+` on 22.x, or `24+` |

Use pnpm `10.34.5`. The CLI's own supported Node range is broader than the generated toolchains' requirements. For a new development environment, Node.js `24.21.0+` satisfies these documented floors.

There is one Cloudflare engine per workspace. `add` refuses selections that would switch the engine or relocate existing runtime source. Anhedral owns composition, account/audience selection, shared packages and independent verification; Void owns its supported provisioning, deployment and code rollback mechanics. Native Void framework features are not implied by deploying Vinext through Void.

Void apps read one private app-root `.env`, copied from `env.example`. Avoid `.env.*` companions and `.dev.vars` in those apps. Wrangler and native Vercel use their generated runtime templates. Keep production secrets server-side; public `VITE_*`, `NEXT_PUBLIC_*` and `EXPO_PUBLIC_*` values are build inputs, not server secrets. Vinext maps `NEXT_PUBLIC_*` into client bundles. The [provider reference](software-factory.md#provider-configuration) describes credential transport and each integration's prerequisites.

### Delivery scope by target

| Target                      | Supported automation                                                                                                                          | Remaining delivery work                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Cloudflare web/API/services | Selected resource setup, bindings/secrets, deployment, provider evidence, verification and recorded code rollback                             | Account/audience selection, product acceptance and data compatibility; rollback does not reverse SQL or restore data |
| Native Next.js/Vercel       | Project connection, environment configuration, CLI delivery or adoption of connected Git deployments, provider evidence and recorded rollback | Eligible account plan, audience protection, repository/CI policy and product acceptance                              |
| Mixed Cloudflare/Vercel     | Cloudflare first, then Vercel, with per-target receipts                                                                                       | Handle partial success; there is no atomic cross-provider release or rollback                                        |
| Expo                        | Explicit platform/profile EAS build, project/source checks, queued-build resume and artifact receipt                                          | Signing, device acceptance, store enrollment and submission; a simulator build is not a store artifact               |
| Electron                    | Local build and packaging scripts                                                                                                             | Platform signing, notarization, installers, updates and distribution                                                 |
| WXT                         | Local extension build and ZIP tooling                                                                                                         | Installed-browser acceptance, store review and publication                                                           |

Hosting audience starts unconfigured and must be selected explicitly. Hosting protection, application authentication and resource authorization are separate decisions. Generated SDK factories and configured provider resources do not establish completed user flows.

The optional Codex inspector uses the same project and service domain logic as the CLI. Opening it reads local configuration and recorded evidence. Live status, analytics and bounded data reads require explicit service actions; supported deletion requires its separate confirmation flow. The inspector is development tooling, not a generated application dependency.

## Source ownership and dependency policy

Generated source belongs to the application and remains editable. Preview bundled additions with `add --dry-run`, `--diff` or `--view`; additions preserve edited/untracked source and record provenance. They require current registry receipts. When `filesChecked: false`, the selection plan is available but a new upstream web bootstrap cannot be previewed offline. Actual installation checks conflicts before committing files.

The catalog in `src/stack-registry.ts` defines composition, `src/dependencies.ts` pins dependencies, and `src/scaffold/` implements recipes. Generated plugin references come from these maintained sources and documents.

Commit the resolved lockfile and any generated `patches/*` plus `pnpm-workspace.yaml` patch mappings. Conditional reviewed patches apply only to `braces@3.0.3` and `node-forge@1.4.0`. `pnpm audit:deps` retains raw upstream findings in `.anhedral-audit-report.json` and blocks high/critical advisories except the exact reviewed advisory/version/patch combinations (`GHSA-vfj7-8cjw-p6xm` and `GHSA-86w9-cpqp-85rv`). Frozen pnpm installation applies patches; detailed runtime regressions belong to this repository's `pnpm test:patch`. These temporary mitigations must be reviewed each release and retired when a compatible verified fix replaces them. Compatible brace-expansion overrides do not create an exception for an affected 3.x consumer.

Validate the resolved dependency graph for each application selection. A clean CLI dependency graph does not establish a clean generated application graph.

## Product requirements

A completed application has server-side resource authorization, private file access, reviewed migrations, meaningful error/loading/empty states and tests for its actual user flows. Jobs and webhooks must tolerate duplicates; paid operations need limits and ownership. Verify the selected runtime and any native packaging, permissions and signing.

Use the [software factory](software-factory.md) for the implementation and acceptance process. Detailed delivery evidence and outstanding live acceptance gaps belong in the [Void verification reference](verification.md#void-delivery-verification) and the application's own verification record, rather than in this architecture standard.
