# Stack standard

This is the architecture standard for applications generated by Anhedral. Use it to select components and decide where code belongs. Follow the [software factory](software-factory.md) to implement and deliver the product.

The default web foundation is Vinext, React, TypeScript, Tailwind, shadcn/ui and Lucide on Cloudflare Workers. Every project uses pnpm workspaces and Turborepo. Add components for a concrete product requirement; the default does not include a database, identity provider or every available service.

## Select the applications

| Need                           | Selection                     | Architecture                                               |
| ------------------------------ | ----------------------------- | ---------------------------------------------------------- |
| Web on Workers                 | Default, or `--vinext`        | Vinext routing and rendering, React UI, Cloudflare runtime |
| Native Next.js on Vercel       | `--next`                      | Next.js server code and Vercel hosting                     |
| Next.js on Workers             | `--next --hosting=cloudflare` | OpenNext adapter and Wrangler delivery                     |
| API shared by multiple clients | `--hono`                      | Hono Worker with OpenAPI contracts                         |
| iOS and Android                | `--expo`                      | Expo, React Native Reusables and NativeWind                |
| Desktop                        | `--electron`                  | Electron and React; platform packaging and signing         |
| Browser extension              | `--wxt`                       | WXT and React popup/Chrome side panel                      |

For example, `--vinext --hono --expo --neon` selects web, an API, mobile and PostgreSQL. `--expo` alone selects mobile. Explicit product flags replace the default selection; required dependencies are resolved automatically. Vinext and Next.js are alternatives. Native Next.js defaults to Vercel; Vinext uses Workers.

Use server routes inside the web app when it is the only consumer. Add Hono when mobile, desktop, extensions or independent clients need a shared API. Browser and device clients access server endpoints; they never import database factories or receive server credentials. Check actual Vinext behavior in its Worker runtime rather than assuming native Next.js parity.

## Select data, identity and services

| Need                                 | Selection                              | Rule                                                                           |
| ------------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------ |
| SQL on Workers                       | `--d1`                                 | Drizzle with D1 bindings; one deployment migration owner                       |
| PostgreSQL                           | `--neon`                               | Drizzle with Neon serverless HTTP; separate transactional migration connection |
| Application identity                 | `--better-auth` or `--clerk`           | Choose one; implement product/resource authorization on the server             |
| Private files                        | `--r2`                                 | Authorize operations through server bindings                                   |
| Cache and configuration              | `--kv`                                 | Eventually consistent; do not use as transactional authority                   |
| WebSocket rooms                      | `--realtime`                           | Cloudflare Durable Objects; define identity and reconnect behavior             |
| Live SQL results                     | `--neon-realtime`                      | Neon sealed-query server/client factories; see below                           |
| Background work                      | `--queues`, `--cron`, `--workflows`    | Define idempotency, retry limits, concurrency and failure recovery             |
| Inference                            | `--workers-ai`, `--openai`, `--ai-sdk` | Server-side calls with explicit model, cost and usage limits                   |
| Transactional email                  | `--resend`                             | Verified sending domain, templates and delivery handling                       |
| Billing                              | `--stripe`, `--revenuecat`             | Application-specific products, entitlements and verified webhooks/purchases    |
| Errors and analytics                 | `--sentry`, `--posthog`, `--basin`     | Initialize SDKs/events and define privacy and operating ownership              |
| Device-local data and shared styling | `--local-data`, `--styling`            | Select for supported client requirements                                       |

D1 is the standard choice when Worker-local SQL fits. Choose Neon when the application needs PostgreSQL semantics. Better Auth supplies application-controlled identity; Clerk supplies hosted identity. Hosting audience protection is a separate access layer from either choice.

The bundled registry is authoritative for exact dependencies, destinations and compatibility:

```sh
anhedral registry list --json
anhedral registry view better-auth --json
anhedral init my-app --vinext --hono --d1 --better-auth --r2 --dry-run --json
```

The resolver rejects conflicting databases/frameworks/identity providers and capabilities without a compatible server. There is no `--all` or external registry support. Recipes create integration foundations; provider resources, credentials and finished features have their own setup and acceptance requirements.

## Organize the source

| Location                                               | Owns                                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `apps/web`, `apps/api`, other selected `apps/*`        | Deployable applications and services, runtime entry points and configuration |
| `packages/ui`                                          | Shared web UI components                                                     |
| `packages/db`                                          | Server-only database factory, schemas and migrations                         |
| `packages/auth`, other selected `packages/*`           | Reusable integration code with explicit inputs                               |
| `packages/typescript-config`, `packages/eslint-config` | Shared tooling conventions                                                   |
| `anhedral.json`                                        | Committed Anhedral configuration and provenance                              |
| `docs/stack.md`                                        | Generated selection, destinations and setup requirements                     |
| `.anhedral/`                                           | Ignored local delivery journals and private state                            |

Use one root `pnpm-lock.yaml` and the root task graph. Keep framework-specific lint dependencies in the consuming app; shared lint configuration stays usable by non-web clients. Shared packages receive bindings, connections and configuration through factories. Extract code around actual consumers, and keep runtime/network relationships explicit.

See the [full-stack example](https://github.com/anhedral/anhedral-cli/tree/main/examples/full-stack) for a source-only composition. It demonstrates the structure; it is not a running production system.

### One Anhedral configuration

The root `anhedral.json` has an envelope with `schemaVersion: 1` and validated named sections. Each section retains its own domain schema. Only selected hosting sections are present.

| Section      | Purpose                                                               |
| ------------ | --------------------------------------------------------------------- |
| `identity`   | Stable application identity and local catalog registration            |
| `setup`      | Products, hosting, environment requirements and owner setup           |
| `standard`   | Scaffold conventions and version provenance                           |
| `registry`   | Recipe versions, generated-file fingerprints and workspace references |
| `providers`  | Nonsecret integration settings and resource selections                |
| `cloudflare` | Delivery engine, account, audience and targets                        |
| `vercel`     | Repository, team, project and audience                                |

Preserve unrelated sections when editing. Credentials and delivery history stay outside this document. Native tooling files remain with their applications: a single Anhedral document does not replace `package.json`, Vite configuration or per-app deployment configuration.

## Data and migrations

All database-backed selections use the server-only `@workspace/db` package:

| Path                            | Responsibility                                        |
| ------------------------------- | ----------------------------------------------------- |
| `packages/db/src/index.ts`      | Factory receiving a D1 binding or connection string   |
| `packages/db/src/schema.ts`     | Shared Drizzle schema, including selected auth tables |
| `packages/db/src/migrate.ts`    | Explicit migration entry point                        |
| `packages/db/drizzle/`          | SQL, snapshots and migration journal                  |
| `packages/db/drizzle.config.ts` | Configuration with paths relative to itself           |

The factory does not load environment files or migrate on startup. Review generated SQL from `pnpm db:generate` before running `pnpm db:migrate`. Both tasks are uncached and excluded from builds and checks. Exactly one server owns deployment migrations; other consumers share the database without becoming migration writers.

D1 manual migration defaults to local. `pnpm db:migrate -- --remote` explicitly targets the configured database in the migration owner's Worker configuration. Void deployment validates an ignored, byte-identical app-local copy against the authoritative shared SQL; the copy is not another migration source.

Neon runtime queries use server-supplied `DATABASE_URL` through the HTTP adapter. Interactive transactions require a reviewed WebSocket or PostgreSQL adapter. Migrations use a transactional WebSocket connection and direct `DATABASE_URL_UNPOOLED` from the environment or `packages/db/.env.local`/`.env`. Test migrations on the intended development branch before production. Runtime provisioning does not supply migration credentials automatically.

## Neon Realtime

`--neon-realtime` selects live PostgreSQL query foundations and adds Neon if no database was chosen. It requires a server and rejects an explicit conflicting database. It can coexist with `--realtime`, which means Durable Object WebSocket rooms.

The recipe creates `@workspace/neon-realtime/server` and `/client` exports in `packages/neon-realtime`. The server receives private `NEON_REALTIME_SECRET` and `DATABASE_URL`; the client receives public `NEON_REALTIME_URL`. Follow the generated package README for framework-specific public environment mapping.

Enable Realtime on the intended Neon branch and configure exact allowed origins, secret and endpoint manually. Authenticate sealing requests, derive user/tenant scope from verified identity, and construct bounded read-only queries on the server. Clients subscribe with short-lived sealed queries; implement authorized renewal, reconnect behavior and isolation tests. No arbitrary SQL endpoint or complete subscription feature is generated.

The pinned integration targets the [Neon Realtime beta](https://neon.com/docs/realtime/overview), whose reviewed authorization model has no RLS support. Scope the queries you seal and review the provider's current limits before production use. Recipe tests do not establish live subscription or cross-tenant acceptance.

## Runtime and delivery configuration

| Profile                                           | Engine and configuration                                                                                                   | Project runtime floor              |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Supported Cloudflare selections                   | Void `0.27.0`; app-local `anhedral.cloudflare.json`, `void.config.ts`, `env.ts`, `env.example`, committed `void.lock.json` | Node.js `24.21.0+`                 |
| Explicit OpenNext, Queues/DLQ or Basin            | Wrangler; app-local `wrangler.jsonc`                                                                                       | Node.js `22.13+` on 22.x, or `24+` |
| Native Next.js/Vercel and other non-Void profiles | Native framework/platform tools                                                                                            | Node.js `22.13+` on 22.x, or `24+` |

Use pnpm `10.34.5`. The CLI's own supported Node range is broader than the generated toolchains' requirements. For a new development environment, Node.js `24.21.0+` satisfies these documented floors.

There is one Cloudflare engine per workspace. `add` refuses selections that would switch the engine or relocate existing runtime source. Anhedral owns composition, account/audience selection, shared packages and independent verification; Void owns its supported provisioning, deployment and code rollback mechanics. Native Void framework features are not implied by deploying Vinext through Void.

Void apps read one private app-root `.env`, copied from `env.example`. Avoid `.env.*` companions and `.dev.vars` in those apps. Wrangler and native Vercel use their generated runtime templates. Keep production secrets server-side; public `VITE_*`, `NEXT_PUBLIC_*` and `EXPO_PUBLIC_*` values are build inputs, not server secrets. Vinext maps `NEXT_PUBLIC_*` into client bundles. The [provider reference](provider-configuration.md) describes credential transport and each integration's prerequisites.

## Source ownership and dependency policy

Generated source belongs to the application and remains editable. Preview bundled additions with `add --dry-run`, `--diff` or `--view`; additions preserve edited/untracked source and record provenance. They require current registry receipts. When `filesChecked: false`, the selection plan is available but a new upstream web bootstrap cannot be previewed offline. Actual installation checks conflicts before committing files.

The catalog in `src/stack-registry.ts` defines composition, `src/dependencies.ts` pins dependencies, and `src/scaffold/` implements recipes. Generated plugin references come from these maintained sources and documents.

Commit the resolved lockfile and any generated `patches/*` plus `pnpm-workspace.yaml` patch mappings. Conditional reviewed patches apply only to `braces@3.0.3` and `node-forge@1.4.0`. `pnpm audit:deps` retains raw upstream findings in `.anhedral-audit-report.json` and blocks high/critical advisories except the exact reviewed advisory/version/patch combinations (`GHSA-vfj7-8cjw-p6xm` and `GHSA-86w9-cpqp-85rv`). Frozen pnpm installation applies patches; detailed runtime regressions belong to this repository's `pnpm test:patch`. These temporary mitigations must be reviewed each release and retired when a compatible verified fix replaces them. Compatible brace-expansion overrides do not create an exception for an affected 3.x consumer.

Validate the resolved dependency graph for each application selection. A clean CLI dependency graph does not establish a clean generated application graph.

## Product requirements

A completed application has server-side resource authorization, private file access, reviewed migrations, meaningful error/loading/empty states and tests for its actual user flows. Jobs and webhooks must tolerate duplicates; paid operations need limits and ownership. Verify the selected runtime and any native packaging, permissions and signing.

Use the [software factory](software-factory.md) for the implementation and acceptance process. Detailed delivery evidence and outstanding live acceptance gaps belong in the [Void verification reference](void-verification.md) and the application's own verification record, rather than in this architecture standard.
